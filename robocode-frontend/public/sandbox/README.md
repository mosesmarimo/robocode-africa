# public/sandbox

Self-hosted WebAssembly runtimes for the browser code-execution tier
(`src/lib/run/`). Nothing in this directory is committed to git — it's
generated by `scripts/copy-sandbox-assets.mjs`, which copies the exact
pinned versions of `pyodide` and `sql.js` (see `package.json`) out of
`node_modules` on every `pnpm dev` / `pnpm build`.

Self-hosting (rather than pointing at a CDN like jsdelivr, which is what
Pyodide/sql.js examples usually do) means:

- no third-party network dependency at runtime — works offline once the
  static assets are cached by the browser;
- a simple CSP (`connect-src`/`script-src 'self'`) instead of allowlisting
  a CDN origin;
- the exact runtime version is pinned and reproducible, matching whatever
  `pyodide`/`sql.js` versions are in `package.json` — no surprise upstream
  changes.

## Regenerating

```sh
node scripts/copy-sandbox-assets.mjs
```

This is also prepended to the `dev` and `build` npm scripts, so it normally
never needs to be run by hand — just after bumping the `pyodide` or
`sql.js` version in `package.json` and running `pnpm install`, if you want
the files on disk before the next `pnpm dev`.

## Layout

```
public/sandbox/
  sql-wasm.js              sql.js's UMD JS glue. Loaded by
                            src/lib/run/run-sql.ts at runtime via a plain
                            injected <script> tag (NOT a static `import
                            initSqlJs from "sql.js"`) — the file has a
                            Node-only fallback path (`require("fs")` /
                            `require("path")`, dead code in a browser) that
                            makes Next's bundler fail to resolve 'fs' if
                            it's imported normally. A <script> tag sidesteps
                            the bundler entirely, exactly like
                            pyodide.js's importScripts() below. Declares a
                            global `window.initSqlJs`.
  sql-wasm.wasm            sql.js's compiled SQLite wasm binary, fetched by
                            initSqlJs's `locateFile` callback once
                            sql-wasm.js has loaded.
  pyodide/
    pyodide.js              Classic (importScripts-able) UMD entry point,
                             loaded by the Web Worker in
                             src/lib/run/run-python.ts via
                             `importScripts("/sandbox/pyodide/pyodide.js")`.
                             Defines a global `loadPyodide()`.
    pyodide.asm.js          Emscripten JS glue, fetched by pyodide.js at
                             runtime relative to `indexURL`.
    pyodide.asm.wasm        The actual CPython + wasm interpreter (~8MB).
    python_stdlib.zip       Python standard library, unpacked into the
                             in-worker virtual filesystem on load.
    pyodide-lock.json       Package lockfile Pyodide reads on load; only
                             matters if code starts loading additional
                             pyodide packages (none are self-hosted here —
                             the v1 Python engine only supports core-stdlib
                             code, no numpy/pandas/micropip installs).
```

## Why these files specifically

`pyodide.js` references exactly these four filenames
(`pyodide.asm.js`, `pyodide.asm.wasm`, `python_stdlib.zip`,
`pyodide-lock.json`) relative to `indexURL`; copying anything less causes a
404 partway through Pyodide's boot sequence. `pyodide.mjs` (the ES module
build) is *not* copied — the worker uses the classic UMD build so it can
`importScripts()` it, which only works in a classic (non-module) Worker.

If a future task needs extra Python packages (numpy, etc.), add the
matching `.whl` file(s) to the `copy()` call for `pyodide/` in
`scripts/copy-sandbox-assets.mjs` and confirm they're listed as
dependencies in `pyodide-lock.json`.

## Not committed to git

These are multi-megabyte binary build artifacts regenerable from
`node_modules` by a one-line script — see `.gitignore`, which excludes
everything in `public/sandbox/` except this README. `pnpm build` (and
`pnpm dev`) always regenerates them first.
